# ORBITclip 7.8.7 — локальный конструктор SQL на основе бизнес-семантики

## Где открыть
**SQL Explorer → Подключение → Таблицы → Бизнес-семантика → Спросить данные ✧**.

### Как пользоваться
1. Подключись к PostgreSQL, выбери рабочие таблицы (до 16 для передачи локальной модели).
2. В «Бизнес-семантика» укажи бизнес-назначение таблиц, зерно (гранулярность), определения полей и метрик, кардинальности ручных связей и термины глоссария.
3. Установи и запусти [Ollama](https://ollama.com/) локально, затем загрузи `ollama pull qwen3:4b` или `ollama pull qwen3:8b` (скачивание модели занимает несколько ГБ).
4. В «Спросить данные ✧» введи имя локальной модели и вопрос, например: «Покажи выручку по клиентам с 1 января 2026 по убыванию».
5. Если модель уточняет период, метрику или статус, ответь текстом и повтори построение.
6. Изучи полученный SQL и объяснение, скопируй в SQL-редактор и отдельно проверь/выполни вручную.

## Как работает
- Все вызовы модели идут на фиксированный **`http://127.0.0.1:11434/api/chat`**. Нет адресов внешних LLM API и нет обязательной облачной регистрации.
- Локальной модели отправляются только метаданные **выбранных** таблиц PostgreSQL, физические имена и типы полей, определения таблиц/полей/метрик, FK, ручные связи, кардинальности, глоссарий и сам введённый вопрос. Пароли, содержимое строк БД и результаты запросов не передаются.
- Модель возвращает **структурированный JSON-план**, а не SQL-код. Локальный компилятор самостоятельно проверяет все таблицы, поля, допустимые агрегаты и метрики по реальному каталогу и сохранённому словарю.
- Поддерживаемый начальный набор: несколько таблиц через существующие FK/ручные связи, явные `LEFT/INNER JOIN`, сохранённые метрики (`SUM/AVG/MIN/MAX/COUNT/COUNT_DISTINCT/COUNT_ROWS`), измерения, простые WHERE/HAVING с литералами, группировка, сортировка, LIMIT.
- При JOIN, способном размножить строки агрегируемой таблицы, генератор **блокирует SQL** вместо выдачи неправильных сумм.
- Если сохранённая метрика содержит неформализованное текстовое условие вроде «без возвратов» или «только оплаченные», компилятор также откажется от SQL. Это принципиально: описания в 7.8.6 ещё не содержат формального определения WHERE; молча игнорировать их нельзя.
- Код не выполняет SQL-запросы и никогда не запускает результаты работы языковой модели. Есть только проверенный черновик и действие «Копировать SQL».
- Запрос к Ollama выполняется в фоне, без подвисания буфера обмена.

## Ограничения и отличие от отдельной SQL Studio 0.13
- Из SQL Studio 0.13 доступно README, но не полная исходная ZIP-сборка. Поэтому это **самостоятельная реализация интеграции в основной SQL Explorer**, а не перенос всех модулей отдельной Studio.
- Пока нет структурированных оконных функций, CTE/подзапросов, автоматической обратной загрузки в графический конструктор, формального редактора условий метрики и автоматического исправления модельных ответов.
- Нельзя гарантировать корректное понимание любого произвольного вопроса: качество зависит от выбранной локальной модели и полноты бизнес-описаний. JSON с неизвестными таблицами/полями отклоняется.
- Этап CI тестирует структурированные ответы модели через имитацию локального Ollama, но **не измеряет качество реальной Qwen3 на пользовательской базе и не выполняет SQL в PostgreSQL**.
- Пользовательские описания и структура БД передаются локальной Ollama только по нажатию кнопки, **не автоматически в фоне**.

## Совместимость
Модуль не изменяет существующие проекты SQL Explorer и сохраняет `~/.orbitclip_sql_projects/`. Остальные функции ORBITclip работают без установленной Ollama. Распространяется накопительным полным ZIP `ORBITclip_CleanInstall_v7_8_7.zip` и патчем `ORBITclip_Patch_v7_8_7.zip` для предыдущей версии.
