# Параллельная разработка ORBITclip

1. **Единый источник** — ветка `main` репозитория `Wolchau/ORBITclip`. Не вести отдельные «окончательные» ZIP без переноса кода в GitHub.
2. Каждая задача из другого чата начинается с чтения `README.md`, `orbit_version.py`, последних коммитов и изменённых файлов.
3. Создавайте отдельную ветку `feature/<краткое-имя>` или `fix/<краткое-имя>`. Не обновляйте `main` напрямую.
4. Открывайте Pull Request с кратким описанием изменений, тестами, совместимостью данных и ссылкой на задачу. Используйте коммиты в PR для согласования параллельной работы.
5. Перед слиянием обновите ветку от `main`, устраните конфликты. Только после проверки сливайте PR.
6. Для каждого пользовательского релиза измените `CLIENT_VERSION` в `orbit_version.py`, добавьте `docs/releases/vX.Y.Z.md`, обновите `patches/vX.Y.Z` для установки на предыдущую версию.
7. После слияния `main` GitHub Actions опубликует release-тег. Уже опубликованный тег не переписывать.
8. **Не включайте в репо** ключи пары, локальные истории, историю сообщений, личные файлы или резервные копии. Общий токен Render — единственное временное тестовое исключение, разрешённое владельцем репозитория.

## Правило безопасности

Любой секрет, однажды опубликованный в ZIP или чате, считается раскрытым.
Используйте индивидуальные токены и штатные секреты GitHub Actions только для CI;
не вставляйте их в клиентские исходники, кроме временного тестового токена в `client_defaults.json` по явному разрешению владельца. Перед публикацией отозвать его и очистить историю коммитов/тегов.

## Правило патчей

Пользователь хочет установочные ZIP-патчи, запускаемые скриптом.
Для v7.2.2 патч лежит в `patches/v7.2.2/`.
При новом выпуске создайте аналогичный патч с манифестом SHA-256, версионной проверкой,
бэкапом и аккуратным откатом при неудаче. Патчи не изменяют пользовательские JSON.
